## Detailed Issue Records

### T-01: Visitor and A/B tracking writes are switched off

- **The ambiguity:** `src/utils/axiosCalls.js:getAbTestVisitorRows` begins with `return null;`, added in `77b3dec5` ("stop get call", 2026-10-10) with no explanation. `src/app/api/track-variant/route.js` treats a `null` lookup as failure, so no visitor row is created or updated in any environment.
- **Potential risk:** someone "fixes" it by deleting the line. The lookup underneath does not filter on `environment` (T-02), and `getEnvironment` can label test as production (T-03), so re-enabling it as written would let test traffic update production rows.
- **Answer (2026-10-22, recommended):** keep it off. The homepage no longer runs a server-side A/B test and GTM carries analytics. Re-enable it only for a new A/B test.
- **What resolves it:** the team confirms the recommendation. If it is ever re-enabled, fix T-02 and T-03 first, then verify with a real write and read against the live table ([DEVELOPMENT](DEVELOPMENT.md) explains why a build alone proves nothing).

### C-01: The old homepage tree still builds but never renders

- **The ambiguity:** `/` has been the static site in `public/new-home/` since `1f911f58`. `src/app/page.js` (A/B variants via `src/utils/getVariant.js`) and `src/app/home/page.js` remain routable in the build output, but the rewrite and the middleware redirect make both unreachable.
- **Potential risk:** deleting them removes the only rollback path. Keeping them means agents may edit code no visitor sees. Older maintainer notes still describe this tree as the homepage.
- **Answer (2026-10-22, decided for now):** keep the tree as the rollback path: reverting merge `cfdae23e` on `main` brings the A/B homepage back. Retire it once the new homepage has run stably for a few weeks. **Never edit these files for homepage changes**; the homepage is `public/new-home/`, exported from `viasocket-site` (`variants/simple-bento`).
- **What resolves it:** a date or condition for retiring it.

### P-05: Paths served by other deployments

- **The ambiguity:** `/help/*`, `/blog`, `/discovery` and `/community` return 200 on viasocket.com but do not exist here. Cloudflare must route them to other projects. Since `b3a7ab32`, `next.config.js` 301s `/help` and every `/help/*` path outside `FOOTER_HELP_PAGES` (`about-us`, `partners`, `plugin-builder`, `security-and-compliance`, `viasocket-embed/billing-partner`) to `/new-direction`. Locally `/help` returns that 301. On production on 2026-10-21, `/help` did too, but other `/help/*` paths were still answered by the help deployment (for example a 404 for `/help/trigger`), so the subpath rule takes effect only for requests that reach this project.
- **Potential risk:** an agent adds a route here that shadows another app, or "fixes" a 404 that is only a 404 locally.
- **Answer (2026-10-22, recommended):** they are other deployments (help centre, blog, discovery app). Old `/help/*` pages redirect to `/new-direction`, except the footer pages.
- **What resolves it:** the team names the repo behind each path. Record it in [05-navigation](05-navigation.md#paths-served-by-other-deployments) and [current-infrastructure/cloudflare](current-infrastructure/cloudflare.md).

## Known Technical Limitations & Verification Gaps

- **No automated tests, lint or typecheck.** The only gates are `npm run build` and HTTP checks of affected routes ([DEVELOPMENT](DEVELOPMENT.md) has the checklist).
- **Visual baseline was HTTP-only.** During preparation the browser pane could not open localhost, so pages were compared by status code, `<title>` and canonical, not by screenshots.
- **Live data dependencies.** Most page content and metadata comes from table-api at request time. Local renders depend on network access and on the values in `.env`; table schemas are verifiable only against the live API.
- **Production-only behaviour.** The Cloudflare cache rule on viasocket.com (for example `/` served `max-age=10800`) does not exist locally or on test. Anything that depends on cookies or per-visitor state must be checked with `curl -D -` against both hosts.
- **No Cloudflare dashboard access.** Per-environment env values and Pages build settings (D-02) could not be read.
